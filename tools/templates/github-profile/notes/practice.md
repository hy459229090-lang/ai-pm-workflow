# 我的工作方式

[← 回到个人介绍](../README.md)

我在产品上的积累来自社区、增长和商业化，现在主要做 C 端 AI 助手。使用 AI 以后，我把一部分原本需要反复协调的取数、制作和检查，接进了自己的日常工作。

这里讲工作深度，不作未经验证的行业排名。以下是不同任务中采用的方法，不表示每个任务都完整跑过所有步骤。

## 先查清楚，再决定做什么

收到一个需求，我会先拆清用户、场景、现有行为和预期改变。通过取数确认影响范围，再借助 AI 读现有代码、接口说明和历史决策，判断已有能力能否复用，成本和限制在哪里。

交给团队的应该是有依据的选择：为什么值得做、可以不做什么、什么条件下需要换方案。数据查询和代码阅读帮助产品判断，但不替代判断。

## 不只交一份文档

方案阶段，我会用 AI 推进交互原型、需求文档和相关配置，把讨论从文字描述变成可以检查的产物。能独立于客户端完成的接口试跑、字段核对、正常与异常返回检查，尽量提前推进。

这里必须区分交付边界：设计示意不等于可运行原型，接口通过不等于完整体验通过；研发实现、联调和最终上线仍由相应责任人确认。

## 不只给最后一句答案打分

评估助手时，我会看完整对话：用户原本要做什么，检索是否跑偏，工具返回能不能支撑回答，上一轮的错误有没有把下一轮带偏。

批量评估把零散反馈变成失败分类和改动清单。机器评分需要人工复核和标准校准；改动后继续回归，不把“回答更长”或“调用成功”当成用户已经解决了问题。

## 工作流不只是一组提示词

我把上下文、执行和检查分开处理：资料要能找到当前版本，历史决策要能追溯；任务要写清目标、输入和验收标准；重复操作沉淀为可复用的能力；产品取舍与发布风险由人确认。

这让 AI 不只负责生成一份文件，还能沿着同一件工作继续查证、制作、检查和复盘。不同任务采用不同深度，不把正在设计的团队自动协作当成已经全面落地。

## 我能一起推进什么

| 你遇到的问题 | 可以一起推进的工作 |
| --- | --- |
| 方向很多，不确定先做什么 | 场景拆解、业务目标、优先级和验证方案 |
| 有想法，但方案落不到实现 | 交互原型、实现约束、接口与配置检查 |
| 助手能回答，但问题反复出现 | 多轮评估、失败归因、改动与回归检查 |
| 团队想用 AI，不想停在写文档 | 选真实任务，接入资料与工具，明确人工决策和验收标准 |

这里只介绍个人能力与工作方式。公司名称仅用于说明任职经历，不代表公司授权、背书或商业合作承诺。具体业务案例与资料需要按相应权限和保密要求另行确认。
