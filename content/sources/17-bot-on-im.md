# 第 17 篇：给工作流开一个 IM 入口 — 在内部 IM 里跑 AI bot

> 一句话：你的 AI 工作流很强，但别人用不起来——因为入口是"打开编辑器敲命令"。把入口搬到团队内部 IM 里，让所有人都能叫得动它。

---

## 一个"只有我能用"的 AI 工作流

毛球 App 的 AI 工作流搭建到现在（前 16 篇），我已经能：

- 一句话让 Agent 写 PRD、拉数据、做评审
- 队列、记忆、版本治理全都有
- 团队知道我有这套东西，经常说"你帮我查下这个数据"

但问题来了——**只有我能用。**

运营想查个数据，得跑来跟我说，我再开编辑器敲数据命令；研发想确认一个需求细节，得等我回复。**AI 工作流的强大，被"入口"卡死了。**

直到我意识到：团队每天都会用的入口是什么？**是内部 IM。** 所有人都在上面，消息即时到达，天然适合"一句话叫 AI 干活"。

于是我做了个决定：**把 AI 工作流接进内部 IM，做一个团队都能调用的 AI bot。**

---

## 这个 bot 长什么样

毛球团队在内部 IM 里加了一个"毛球助手"，任何人都能@它：

> **运营**："@毛球助手 查一下上周宠物美容的预约量"
> **研发**："@毛球助手 宠物问答的冷启动方案定稿了吗？"
> **我**："@毛球助手 跑一下宠物美容预约的评审"

它在 IM 里直接回 Markdown 格式的结果。**门槛从"会敲命令"降到了"会发消息"。**

---

## 核心架构：一条消息的旅程

bot 看起来简单，背后是一条完整链路。这是最关键的架构理解：

```
用户在 IM 发消息
    ↓
IM 消息 → 桥接服务（监听 IM 消息流）
    ↓
写入收件箱（inbox）
    ↓
AI 会话处理（识别意图 → 调对应能力）
    ↓
结果写入发件箱（outbox）
    ↓
发送服务 → 回 IM 消息
```

**三个设计决策**：

1. **桥接（Bridge）**：一个常驻服务监听 IM 消息流，把消息转成 AI 能处理的格式。它是"IM 和 AI 之间的翻译官"。

2. **收件箱/发件箱（inbox/outbox）**：消息先落到本地队列，AI 处理完再发。**不是实时转发**——中间加一层，断了能补发、能追溯、能并发。

3. **单通道回复**：发送只走一条通道，避免两条链路同时回导致消息重复。

---

## 消息分流：三秒判断，不浪费 AI 的思考

bot 收到一条消息，第一件事是**判断它值不值得 AI 认真处理**。这是整个 bot 最省成本的设计：

| 级别 | 特征 | 处理方式 |
|------|------|---------|
| **L1 简单问答** | 闲聊/自我介绍/查已有文档 | 直接回，不开后台任务 |
| **L2 要查数据/分析** | "查一下上周预约量" | 秒回"收到，预计 3 分钟" → 派后台子任务跑 → 汇总一条交付 |
| **L3 口径模糊** | 一句话多种理解 | 立即回澄清，列 2-3 种口径选项，等用户选，不猜 |

**配套三条铁律**：
- **先收口再跑数**：口径不确定先确认，不带着歧义开跑
- **先查已有资产**：历史报告/SQL 能复用就先复用，不每次都现查
- **子任务不回群**：所有后台结果统一由主会话汇总成一条消息，杜绝碎片化刷屏

### 秒回通道：客套话别打扰 AI

IM 里全是"在吗""谢谢""测试"这种短消息。让它们唤醒 AI 会话纯属浪费。

桥接层内置一张**精确关键词表**（限 ≤12 字的短消息），命中就直接由桥接回复——**不写消息队列、不唤醒 AI 会话**。

```
"在吗" → "在的，有什么需要帮忙？"
"谢谢" → "不客气~"
```

**高频低价值消息在入口处拦掉，AI 只处理真正需要思考的消息。**

### 并发池：同时最多 3 个任务

后台子任务同时跑的上限要控制（比如 3 个）：
- 第 4 条到达 → 登记排队 + ack"排队中，前面 N 个"
- 有空位 → 先进先出取下一个
- **同源合并**：同一对象 60 秒内的连续话题 → 不新开任务，追加进原任务
- **超时兜底**：任务 N 分钟无返回 → 标失败发失败回复，不让用户干等

---

## 让 bot 不"死机"：守护进程

bot 跑在服务器上，一定会挂。关键是挂了能**自己爬起来**。

毛球 bot 的守护设计：

```
守护进程（Watchdog）
  ├─ 常驻，监控桥接是否存活
  ├─ 桥接挂掉 → 自动拉起（子进程方式）
  ├─ 连续 5 次重启失败 → 告警
  └─ 禁止手动启动桥接（会造出第二个实例 → 消息重复）
```

**这条很重要**：手动启动会造出第二个实例，每条消息收两遍、回两遍。守护进程统一管理，**只有它一个能拉起桥接。**

### 半死检测：进程活着，功能死了

比进程崩溃更隐蔽的是**半死（zombie）**——进程还活着、看起来正常，但消息既不进也不出。

**判据不是进程存活，而是心跳新鲜度**：

```
桥接自己维护心跳表
守护进程每隔 N 秒读"发送线程心跳"
  ├─ 心跳超时（如 90 秒没跳）→ 判僵尸 → 强杀重启
  └─ 心跳在跳但发送卡死 → 查发送队列兜底：
      某条消息卡在"发送中"超阈值 → 重置为待发 → 重启后由新发送线程补投
```

**为什么不重投会重复**：发送 API 返回成功瞬间立即回写"已发送"，所以停在"发送中"的必是平台没收到——重投是安全的。

### 半死排查三板斧

进程活着但消息不进不出时，按顺序查三处：
1. **桥接日志**有没有最近的重连成功记录（名义连接是否假死）
2. **消息队列**是否长时间不增长（收方向断了）
3. **发送队列** pending 是否持续增长（发方向断了）

解法：**只杀桥接、不杀守护**——让守护用最新代码自动拉起。

### 健康检查

健康检查指令（在 IM 里发 `/health`）：
- 桥接是否存活
- 守护是否存活
- 收件箱最后活跃时间
- 本批消息处理了几条
- 有没有堆积的未回复消息

**问题暴露得越早，修复越容易。**

## 让 bot 有记忆：三层工作区

bot 面对的是**多个人、多个群**——每个实体的上下文是隔离的。

毛球的 bot 记忆设计（配合第 16 篇的三层记忆）：

| 记忆范围 | 存什么 | 怎么用 |
|---------|--------|--------|
| **群级** | 这个群的历史讨论、结论 | 群里问"上周定的预约规则"，bot 从群记忆召回 |
| **人级** | 这个人问过什么、偏好 | 运营老问预约数据 → bot 记住，下次直接给 |
| **bot 级** | bot 自己处理过的任务、踩过的坑 | bot 越用越懂，不重复犯错 |

### 记忆不是自动有的，是"整理"出来的

关键设计：**聊天记录全量留存（原材料），定期整理成记忆（蒸馏产物）。** 不是把全部聊天塞进上下文。

```
记录：聊天记录全量留存，长期不清理（兜底：整理漏了随时可补）
  ↓
整理：未整理消息攒够 N 条（如 15 条）→ 打"待整理"标记
      → 按人/群归集 → 批量抽取四类内容 → 写入记忆表 → 标记已整理
      （批量比逐条好：一次看一批上下文，判断更准、token 更省）
  ↓
记忆生效：桥接收消息时，把该人/群记忆摘要（每实体 ≤100 字）
          注入消息一并带给 AI —— AI 什么都不用做，看见消息就自带记忆
```

### 只记四类内容

整理时，只把四样东西写进记忆（由 AI 判断，闲聊不写）：

| 类型 | 内容 | 例子 |
|------|------|------|
| **画像** | 稳定属性 | "运营-小美，负责预约转化" |
| **进行中** | 活跃话题/待跟进 | "在等预约量周报" |
| **事实结论** | 长期有效的口径/约定 | "预约同一时段只允许一单" |
| **工具映射** | 什么问题走什么工具 | "查预约量 → 数据脚本 A" |

### 两级召回

- **轻量前置**：桥接注入 ≤100 字摘要，不依赖 AI 自觉
- **深度检索**：追问历史细节时，全量读该实体条目（量小，不上向量检索）

## 回复格式：IM 的礼仪

bot 回复 IM 消息，格式要有讲究（和写文档不一样）：

- **禁用 Markdown 大标题**（`#`/`##`）——在 IM 客户端渲染后字号过大，像在喊
- **用粗体做段落标签**、`•` 做列表、`>` 做引用
- **每条消息至少一个加粗锚点**（结论/核心数字/行动点）——保证对方扫读 1 秒能抓到信息
- 表格只在数据维度多且需反复对照时才用

毛球的例子：

> **预约量：上周 1,240 单，环比 +18%**
> • 城西店 380 单（+25%）/ 城东店 290 单（+12%）
> 换毛季活动上线后增长明显，建议下周继续投放。

先给结论，再给明细——IM 用户没耐心读长文。

### 按消息类型说话

IM 消息不只是文本。bot 收到不同消息类型，要有不同反应：

| 消息类型 | bot 的处理 |
|---------|-----------|
| 文本 | 正常处理 |
| 语音/视频 | 如实告知"收到了但看不了，要我做什么" |
| 文件 | 能下载解析就处理，解析不了如实告知（**不编造内容**） |
| 引用 | 结合被引用原文的上下文回，默认不引用（除非不指着某条对方听不懂） |
| 撤回 | 注销该消息的待发回复，不回复撤回本身 |

**核心自检**：对方在手机上看到这条消息舒不舒服？

## 多 bot 协作：交接协议

当系统规模变大，可能出现多个 bot（比如一个管数据、一个管需求）。它们之间怎么协作？

毛球的约定（脱敏表述）：
- **交接靠"上下文包"**：六段结构化文本，把任务背景、已做动作、待办、依赖全带上
- **必须 @ 对方**：光发消息不 @，对方可能不理
- **文件先上传发链接**：不传本机路径（对方机器上没这个路径）
- **触发词**：「交接给 XX」

**多个 bot 不是一个群，是有协议的单兵协作。**

---

## 什么时候才需要做这个

诚实地说，**不是所有团队都该立刻上 bot。** 判断标准：

| 条件 | 说明 |
|------|------|
| 团队多人需要调 AI 能力 | 只有你用 → 先别做，成本大于收益 |
| 内部 IM 有开放接口/机器人能力 | 没有 → 做不了（或要自己做桥接） |
| 你已经有稳定的 AI 工作流 | bot 是入口，不是能力本身——能力没搭好，入口没意义 |
| 有资源维护常驻服务 | bot 是常驻服务，要监控、要运维 |

毛球是在**前 16 篇的能力搭好之后**才做的入口。**顺序别反：先有能力，再开入口。**

## 自查清单

- [ ] 已有稳定的 AI 工作流能力（不是零基础直接上 bot）
- [ ] 内部 IM 有可接入的机器人能力
- [ ] 架构理解：桥接 → 收件箱 → AI 会话 → 发件箱 → 发送
- [ ] 有守护进程，挂了自动拉起，不手动启动第二个实例
- [ ] 有健康检查（/health 或等效）
- [ ] 记忆按群/人/bot 隔离，蒸馏后使用
- [ ] 回复格式符合 IM 礼仪（结论先行、加粗锚点）
- [ ] 多 bot 场景有交接协议
