# 第 13 篇：编排与门禁 — 让多 Agent 协作有序可控

> 一句话：第 05 篇讲拉团队，这篇讲怎么管团队——不是"分派完就撒手"，而是用编排和门禁让协作不出轨。

---

## 上一版的教训：管 AI 比 AI 干活还累

第 05 篇讲了毛球拉 Agent Team 的翻车经历——14 个 AI 一起干，PM 变成人肉路由器。

后来我做了改进：设队长、定输入输出、设评审点。**但问题还没根除。**

毛球推荐 feed 改版，队长（协调者）把任务分下去后：

- 需求收口 Agent 还没确认信息完整，PRD Agent 就开始写了——写出来的背景全是错的
- 技术 Agent 发现一个假设没验证，直接按"合理假设"继续设计——但那个假设是错的
- 运营评审和规范性检查混在一起，一份产出既过运营关又过质量关，两边标准互相打架
- 我每天打开队列，看到一堆"进行中"，但不知道哪个真正动起来了、哪个卡着

**问题在哪？** 我设了队长、设了关卡，但**没有一个明确的"开工门禁"**——谁在什么条件下才能开始干活，没有规定死。

---

## 编排（Orchestration）是什么

第 05 篇的结论是"设一个队长"。但队长怎么干活？这就叫**编排**。

编排不是"分配任务"，而是**定义协作的节奏和门禁**：

1. **任何新工作，先出计划，不立即执行**（Plan First）
2. **计划要过审批，审批通过才开工**（Launch Gate）
3. **派活前先做角色扫描**——判断哪些角色需要介入，不派多余的人
4. **关键分歧用多视角审议**——不靠单一角色拍脑袋

这一篇讲的就是这套编排机制。

---

## 机制 1：Plan First — 任何新工作先出计划

收到任何新工作，第一步永远是**制定计划，不立即执行**。

毛球的例子：你说"我想给附近服务加一个宠物美容预约功能"。

协调者（队长）**不会**直接说"好的，PRD Agent 去写"。它会先输出一份计划：

```markdown
## 目标理解
给附近服务加宠物美容预约：用户浏览美容服务 → 选择门店 → 预约时间 → 到店核销

## 信息缺口（需要你提供的）
1. 宠物美容的定价规则？（按次/按项目）
2. 预约冲突怎么处理？（同一时段多人抢）
3. 是否要接入支付？（还是到店付）

## 参与角色（角色扫描结论）
- PRD Agent：写需求文档（需要）
- 技术 Agent：可实施性评估（需要——涉及预约状态机）
- 数据 Agent：埋点方案（需要）
- 运营 Agent：暂不需要（无活动/文案）

## 执行步骤
1. 需求收口 Agent 补齐信息缺口
2. PRD Agent 出主 PRD
3. 技术 Agent + 数据 Agent 并行
4. 三视角审议 → 规范性检查 → 交你拍板

## 预期产出物
- docs/prd/宠物美容预约/宠物美容预约_PRD.md
- docs/prd/宠物美容预约/spec/预约状态机_Spec.md

## 已知风险
- 预约状态机较复杂，技术评估若发现现有表结构不支持，需回退方案
```

**这一步的意义**：把"要做什么、缺什么信息、谁参与、怎么做、产出什么、风险在哪"在动手前全部摊开。**计划这一步，过滤掉 90% 的白干。**

---

## 机制 2：Launch Gate — 审批通过后的强制门禁

计划通过审批后，开工前还要过一次"门禁"——逐项打勾，任何一项不过就不能开始：

```markdown
## 开工门禁（Launch Gate）
- [ ] 输入文档都存在且路径可访问
- [ ] 已读当前正本入口，确认用的是最新版本
- [ ] 角色扫描中"需要"的角色全部出现在执行步骤里
- [ ] 信息缺口已填补，或明确标注"可假设"
- [ ] 第一步的任务描述、输入路径、产出路径已明确
- [ ] 无未解除的阻塞项
```

**关键规则：门禁不过，不能边做边补。** 过去我总是"先让它干着，缺的信息边做边补"——结果每次都返工。现在规定死：门禁过不了，就停下来补，补完再开工。

毛球的实战：有一次宠物美容预约的信息缺口里"预约冲突怎么处理"没填，门禁卡住。协调者没有直接开工，而是把问题列出来问我。我确认"同一时段只允许一单，冲突提示改选时间"——然后才开工。**多问一句，避免了技术 Agent 设计一版错误的状态机。**

---

## 机制 3：角色扫描 — 不派多余的人

派活前，逐个角色问一句"这个任务需要你吗"：

| 角色 | 判断问题 |
|------|---------|
| 需求收口 | 原始需求信息完整吗？需要先补齐吗？ |
| 技术评估 | 有需要验证的技术假设吗？ |
| 调研 | 需要竞品/行业信息支撑吗？ |
| 交互设计 | 需要交互方案或 Demo 吗？ |
| 可实施性 | 需要从研发视角检查工程盲区吗？ |
| 三视角审议 | 会涉及方向性分歧，需要多视角审视吗？ |
| 汇报 | 需要面向领导的汇报材料吗？ |
| 数据 | 需要取数验证吗？ |
| 运营评审 | 涉及文案/活动策略吗？ |

**规则：角色扫描"需要"的角色，必须出现在执行步骤里；不需要的，一个都不多派。**

毛球的实际感受：扫描做多了，发现很多任务根本不需要 5 个角色。宠物美容预约这种常规功能，3 个角色就够——**人少，沟通成本低，产出反而更快**。

---

## 机制 4：三视角审议 — 关键分歧不靠一个人拍

当任务涉及方向性决策（比如推荐算法选型、定价策略），单个角色拍脑袋容易偏。用三个固定视角并行审议：

| 视角 | 关注什么 | 毛球宠物美容的例子 |
|------|---------|-------------------|
| **技术** | 可行性、成本、风险 | "预约状态机用现有表能实现吗？并发冲突怎么防？" |
| **用户** | 体验、需求、痛点 | "用户会想线上支付还是到店付？预约要几步？" |
| **商业** | 收益、成本、战略 | "美容预约能带来多少收入？引流还是赚钱？" |

三个视角各自陈述 → 汇总共识与分歧 → **共识直接采纳，分歧列给 PM 拍板**。

**这条最关键**：三视角审议不是"投票决定"，而是"帮你把分歧看清楚"。最终决策还是人做——符合本系列核心理念第三条"AI 是副驾驶"。

---

## 效果对比

| 指标 | 只有队长（05 篇） | 编排 + 门禁（本篇） |
|------|-----------------|-------------------|
| 开工前是否确认信息 | 有时不确认就干 | 强制 Plan First + 门禁 |
| 是否派多余角色 | 常拉一堆人 | 角色扫描，按需派 |
| 方向性分歧 | 队长/评审一个人定 | 三视角审议后交人拍板 |
| 信息缺口 | 边做边补，返工 | 门禁卡住，补齐再开工 |
| PM 的介入 | 随时被问 | 只在三个时机：批计划/解阻塞/审产出 |

---

## 自查清单

- [ ] 任何新工作先出计划，不立即执行
- [ ] 计划包含：目标理解 / 信息缺口 / 参与角色 / 执行步骤 / 预期产出物 / 已知风险
- [ ] 开工门禁逐项打勾，不过不开工（不边做边补）
- [ ] 角色扫描做过，"需要"的角色都在步骤里，不需要的不派
- [ ] 方向性分歧走三视角审议，共识采纳、分歧交人拍板
- [ ] 真实跑过一个任务，验证门禁确实挡住过一次返工
